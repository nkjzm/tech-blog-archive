# 記事生成と推敲の材料

記事の正本は `../articles/` に置く。このフォルダは、AIが初稿を書いた記事だけを対象に、初稿と修正後の差から次の初稿を改善するための資料庫。Zenn・Qiitaへ公開する記事本体とは分けて管理する。

## 記事を生成するとき

1. このREADMEと `pairs/` の `usableForGeneration: true` のペアを読む。各ペアの `before` / `after` を `index.json` のcommit・pathと照合し、対応するsnapshotを比較する。
2. 語り方や説明の順序、削った説明・足した具体例を今回の構成の参考にする。過去の記事内容、古い技術条件、個別記事だけの表現をそのまま転用しない。
3. Gitの作者名だけでAI初稿・人間修正を判断しない。Co-Authored-ByはAIが関与した証拠であり、全文AI執筆の証明ではない。過去の修正から、本人が確認していない一般的な好みを勝手に確定しない。
4. 新しい記事は `articles/` に作る。公開操作・公開状態は記事のfrontmatterで管理し、この資料庫の採用可否と混同しない。

## 構成

- `sources.json`: AIが初稿を書いた記事の明示的な対象一覧。`articlePath`・`initialDraftCommit`・判断根拠の`evidence`を管理する。未登録の記事は抽出しない。
- `index.json`: ローカルに存在する全Git refsから抽出した登録記事の履歴。コミット、時刻、当時のpath・blob、追加・修正・削除・再追加、本文変更とfrontmatterだけの変更を記録する。
- `snapshots/<記事ID>/<blob SHA>.md`: コミット済みの原文。frontmatterだけが違う版も保存し、同じ記事の同じblobは一度だけ保存する。
- `pairs/*.json`: 生成で参照する変更前後とその根拠を手動管理する。原文は重複保存せず、commit・pathからindexのsnapshotへたどる。

`index.json` と `snapshots/` は生成物なので直接編集しない。`pairs/` は抽出で上書きされない。

## 履歴を更新する

```bash
node scripts/export-writing-history.mjs
```

Node.jsの標準機能とGitだけで実行できる。shallow cloneは履歴欠落を防ぐため拒否する。未取得のリモート履歴や失われたコミット、未コミットの作業ファイル、reflogだけに残る履歴は対象外。必要なリモート履歴を取得した後で実行する。

全ローカルrefsの到達可能コミットを走査し、`sources.json` に登録した記事に変更があるコミットのみをindexへ収録する。登録した初稿コミットが到達可能で、その記事を含むことも確認する。AIが題材の記事でも、人間が初稿を書いた記事や執筆主体が不明な記事は対象に追加しない。履歴資料だけをコミットしても生成結果が変わらないよう、現在のHEAD・生成時刻・記事を変更しないコミットの件数は出力しない。mergeは各parentとの差分を記録するので、同じcommitにparentごとのイベントがある。

記事IDは当時のpathのファイル名。renameを同一記事へ自動統合しないため、rename時は別IDとなる。新pathも対象にする場合はsources.jsonへの登録が必要。削除前の版も保持し、祖先に同じpathがあれば再追加として記録する。再生成は既存の資料を削除しないため、refsの削除で到達不能になったsnapshotが残る場合がある。対象一覧を縮小しても古いsnapshotは自動削除しない。縮小時は、変更前のindexに記録された生成物のうち対象外になったものだけを確認して削除する。その時点の抽出対象はindexを正とする。

本文とfrontmatterは先頭の `---` ブロックで分離して比較する。本文の空白や改行も変更に含む。自動同期によるfrontmatter変更も監査資料として保持するが、人間の推敲とは扱わない。`attribution` は明示的な自動化表記・AI coauthorの有無による機械分類で、それ以外は `unknown` とする。

## 今後の初稿と人間修正を残す

1. AIによる初稿ができた時点で、本人が修正する前にコミットする。メッセージに `writing: AI初稿 <記事ID>` を含め、AI関与のCo-Authored-Byを残す。そのコミットのSHA・記事path・AI初稿である根拠を `sources.json` に追加する。初稿は先にコミットし、そのSHAを登録する。指示や記事の目的など比較に必要な背景は、ペアJSONの `context` に要点を書く。秘密情報や会話全文は入れない。
2. 人間の推敲中は `articles/` の正本を直接編集する。AIが本人の作業中の変更を整形・巻き戻ししない。
3. 本人が「修正完了」「この版を採用」と確認した版を、`writing: 人間修正確定 <記事ID>` を含むメッセージでコミットする。途中でAIも直したなら、その区間を純粋な人間修正とは呼ばず内訳を記録する。
4. 抽出スクリプトを再実行し、`pairs/<記事ID>.json` に初稿・直接の変更前・確定稿のcommitとpath、主体を判断した根拠、本人の確定確認の有無、利用可否を登録する。コミットメッセージだけが根拠の過去資料には `confirmedByUser: false` を付ける。
5. 初回Git版が執筆初稿とは限らない。取り込み記事・削除後の再追加・公開フラグやIDだけの変更・自動同期・主体不明の修正は自動で採用ペアにしない。

対象はClaude Code Skills・プライバシーポリシー監査・PreToolUse・Aqua Voiceの4記事。登録した記事のコミット済み全版を保存することと、人間の推敲教材として採用できることは別。現時点では根拠のある2件を候補として登録している。Aqua Voice記事のコミット済みの修正はAI作業であり、人間修正ペアには登録していない。本人の未コミット修正は確定・コミット後に追加する。

## 比較例

ペアの `before.commit` / `after.commit` を使って差分を確認する。

```bash
git diff <before.commit> <after.commit> -- <articlePath>
```

差分を読み、今回の生成に活かせる変更かを個別に判断する。採用候補は「Claude Code SkillsをGitHub Actionsで実行する記事」と「プライバシーポリシー監査記事」。後者は初回保存版から確定版までの間にAI修正を含むため、人間修正の直接比較には直前の版を使う。
